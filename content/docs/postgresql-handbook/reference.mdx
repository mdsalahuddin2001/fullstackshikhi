## Distinctions worth remembering

| Often confused | Difference |
| --- | --- |
| Database vs DBMS | Organized data vs software that manages it |
| SQL vs PostgreSQL | Language vs database product |
| NULL vs zero/empty | Unknown/absent vs known value |
| WHERE vs HAVING | Row filter vs group filter |
| GROUP BY vs window | Collapses rows vs annotates rows |
| Primary key vs identity | Uniqueness rule vs value generation |
| Constraint vs validation | Durable rule for all writers vs boundary feedback |
| Transaction vs serializable behavior | Atomic grouping vs concurrency guarantee |
| Index vs cache | Access structure vs stored/reused data or results |
| Migration vs seed | Structure transition vs data population |
| Replica vs backup | Following changes vs recoverable historical state |
| Authentication vs authorization | Who you are vs what you may do |

## Retrieval practice

Close the handbook and answer these, then use the linked chapter to check yourself:

1. Why does `COUNT(city)` return 3 while `COUNT(*)` returns 4? **NULL is not counted by the column aggregate.**
2. Why can a left join lose Sami? **A WHERE predicate on a missing right row can reject the NULL-extended row.**
3. Why snapshot unit prices? **Past orders must retain the agreed price after catalog changes.**
4. Why does a transaction use one pool client? **Transaction state belongs to one database session.**
5. Why might a sequential scan be correct? **Reading a large fraction of a table can cost less than indexed access.**
6. Why test RLS as a non-owner? **Owners and privileged roles can bypass its filtering.**
7. Why isn't a replica enough for recovery? **It can replicate the same unwanted changes.**
8. What proves a backup works? **A successful restore plus data and application checks within recovery targets.**

Revisit after one day, one week, and one month. Change the dataset: add ties, missing relations, empty groups, and concurrent updates. These expose assumptions that a happy-path example can hide.
