## A query is a plan, not a single operation

PostgreSQL parses SQL, plans a strategy using estimates, and executes operators such as scans, joins, sorts, and aggregates. A sequential scan reads the table; an index helps locate selected entries but may require extra table reads. Reading most of a small table can be cheaper than using an index.

`EXPLAIN` shows estimates without executing the query. `EXPLAIN ANALYZE` actually runs it. Use the latter carefully with mutations; even a rolled-back execution can have effects such as consumed sequence values.

## The million-row lab

Run this in your learning database. It creates a separate table and leaves the shop seed untouched. It needs disk space and may take a little time.

```sql
CREATE TABLE handbook.events_lab AS
SELECT n AS id,
       (n % 1000)::integer AS tenant_id,
       timestamptz '2026-01-01 00:00:00+00' + n * interval '1 second' AS created_at,
       repeat('x',100) AS payload
FROM generate_series(1,1000000) AS n;
ANALYZE handbook.events_lab;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at FROM handbook.events_lab
WHERE tenant_id=42 ORDER BY created_at DESC,id DESC LIMIT 20;

CREATE INDEX events_lab_tenant_recent
ON handbook.events_lab(tenant_id,created_at DESC,id DESC);
ANALYZE handbook.events_lab;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at FROM handbook.events_lab
WHERE tenant_id=42 ORDER BY created_at DESC,id DESC LIMIT 20;
```

Expected result regardless of plan: 20 rows, beginning with ID 999042, then 998042. Capture both plans. The index aligns equality on tenant with the ordered suffix, allowing a short ordered scan. Exact timings and selected plan vary with hardware, cache, statistics, configuration, and PostgreSQL version. Do not invent a promised speedup.

## Read the plan like evidence

- Compare **estimated rows** with **actual rows**. Large errors suggest stale statistics, correlated predicates, or an unsuitable model.
- Check **loops**: a cheap inner operation repeated thousands of times can dominate.
- Inspect **buffers**: shared hits are cached blocks; reads involve loading blocks. Neither is a direct business latency guarantee.
- Find **sorts** and spilled temporary work; avoid globally increasing memory without considering concurrent queries.
- Look at rows removed by filters and work performed before `LIMIT` can stop the query.

Run multiple trials and record warm/cold context. Do not compare a first cold run to a later warm run and attribute the entire difference to an index.

## Choose an index for an access pattern

| Tool | Useful for | Trade-off |
| --- | --- | --- |
| B-tree | Equality, ranges, ordering | Extra writes and storage |
| Composite | Multiple predicates and order | Leading columns strongly affect usefulness |
| Unique | Enforcing uniqueness and lookups | Rejects conflicting writes |
| Partial | A frequently queried subset | Query predicate must imply index predicate |
| Expression | Queries such as `lower(email)` | Query expression must match appropriately |
| GIN | JSONB containment, arrays, full-text search | Write/maintenance overhead |
| GiST | Spatial/range search with suitable operator classes | Specialized semantics and workload |
| BRIN | Huge physically correlated tables | Lossy block-range summaries; rechecks |

```sql
-- Optional shop examples; use only after identifying the query.
CREATE INDEX orders_pending_recent ON handbook.orders(created_at,id)
WHERE status='pending';
CREATE INDEX customers_lower_email ON handbook.customers(lower(email));
CREATE INDEX products_attributes ON handbook.products USING gin(attributes);
```

An index on `(tenant_id, created_at, id)` is not a universal answer for queries filtering only an unrelated column. More indexes also mean slower inserts, more vacuum work, and larger backups.

## Maintenance and application patterns

`ANALYZE` refreshes planner statistics. Ordinary `VACUUM` makes dead-tuple space reusable and supports visibility maintenance; it generally does not shrink the table file back to the OS. Autovacuum does this routinely, but long-running transactions can prevent cleanup. `VACUUM FULL` rewrites and locks the table; it is not routine first aid.

An **N+1 query** loads orders once, then makes a separate query for each order's items. Batch with a join or `WHERE order_id = ANY($1)` when appropriate. Measure network round trips as well as database time. Offset pagination scans/discards preceding entries; keyset pagination can seek after the previous key.

`pg_stat_statements` aggregates query workload statistics after server-side setup (including preload configuration). In an environment where it is enabled, inspect high total execution time and high call counts, then examine representative queries. Do not assume that `CREATE EXTENSION` alone is sufficient on every server.

## Challenge · Defend your index

For the million-row query, explain why tenant comes first and both sort columns follow. Compare `OFFSET 900` with a cursor after a known `(created_at,id)` pair. Save plans and state whether both queries return the same logical page under a fixed dataset.

<summary>Worked reasoning and cursor query</summary>

Tenant equality restricts the range; the remaining index order matches recent events. ID creates a stable tie-breaker if timestamps tie. For descending order, the next page uses a less-than comparison.

```sql
SELECT id,created_at FROM handbook.events_lab
WHERE tenant_id=42
 AND (created_at,id) < (
  timestamptz '2026-01-01 00:00:00+00' + 980042 * interval '1 second',980042
 )
ORDER BY created_at DESC,id DESC LIMIT 20;
```

This continues after the first page's twentieth row. The next first ID is 979042. An offset query for that same next page uses `OFFSET 20`; an offset of 900 is a separate deep-page experiment. Fetch the actual row at the boundary before constructing its equivalent cursor.
